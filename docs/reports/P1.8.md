# P1.8 report: places from GPS (offline reverse geocoding) and place-aware search

- **Phase A** (code and tests): 2026-10-21, branch `p1.8` in `.worktrees/p1.8`, rebased on `main` at `9c0fdfe`
  (P3-T merged and reviewed).
- **Phase B** (merge, real run, evals): 2026-10-21 on `main`. `p1.8` needed no new rebase (main hadn't moved),
  was fast-forwarded, and the worktree was removed.

## Summary

- **`imgsearch geo download`** fetches the GeoNames files once into git-ignored `data/geo/`:
  - `IN.zip`, `admin1CodesASCII.txt`, `admin2Codes.txt` and `countryInfo.txt`, 18 MB in all.
  - A file already there is skipped; `--force` downloads it again.
  - `MANIFEST.tsv` records each file's size, SHA-256, URL and download time.
  - The zip is read in place, never extracted.
- **`places` stage** (no model, no pen drive, `requires: ["ingest"]`):
  - For each photo with GPS it records the nearest city, its district, state and country, and the nearest
    landmark within 0.5 km, with distances.
  - Uses numpy haversine over a bounding box. No new dependencies.
  - Migration 005: `photo_places`, `places`, `place_names`. The names also go into `text_fts` as kind `place`.
  - Runs in `imgsearch run places` and in `update` after `filename`. `status` shows GPS coverage.
- **Real run:** all 908 GPS photos resolved (890 with a city, all 908 with district and state), 49 with a
  landmark. The 1,442-photo run took 5.1 s in all, including startup and the GeoNames load (about 5.6 ms per
  GPS photo); peak RSS 275 MB.
- **Every result shows its date and place**, in the CLI and in the bot's captions:
  `2022-09-12 · Anjuna, North Goa, Goa`.
- **Place resolution.** The rewriter's `place` counts only if it resolves, through `place_names` (GeoNames names
  and alternate names, any script), to a place some photo was taken at. Real checks:
  - Goa, गोवा, Pune, Mussoorie, Delhi and दिल्ली resolve.
  - Gurgaon → Gurugram, Lal Qila → Red Fort, Ladakh, Lotus Temple and India Gate resolve.
  - "Jaipur" and "Noida" don't: no photo's GPS city or district has those names.
- **The place filter is off by default (rule 14).** With `--place-filter` it keeps only photos from the place
  or whose text names it, combined with the date filter, and falls back place first, then date.
  - vector+rw recall@5 on the 10 place queries: 0.74 without the filter, 0.64 with it. The old 53 dropped 0.02.
  - So `search.place_filter: false`. `--place-filter/--no-place-filter` on `search` and `eval`.
- **Eval:** vector+rw (the default) is unchanged on the 53 old queries (0.79). All 57: 0.80. The 4 new place
  queries score 1.00 with or without the filter. Details in `docs/eval/baseline-p1.8.md`.
- **P3-T review T5:** SigLIP loads with `local_files_only=True` (no Hub request per load). Search's model load
  was 4.0–4.7 s afterwards.
- **Tests:** 542 pass (main had 486 before P1.8), ruff clean. All new tests use synthetic GeoNames files in
  `tmp_path` and an `httpx.MockTransport`.

## Changes from the plan

All recorded in the plan (new D22; P1.8 entries in "Changes during build"):

- **Interface changes:**
  - `ParsedQuery.place_filter` (new `PlaceFilter` type), set by `Searcher`. Every `Retriever` must honour it,
    as with `date_range`.
  - `Result.date` and `Result.place`.
  - `SearchResponse.place_filter` / `place_fallback`.
  - `Searcher.search(place_filter=None)`: None means `search.place_filter` from config.
- **The place filter is off by default** (phase B, rule 14): new `search.place_filter: false`;
  `--place-filter/--no-place-filter` on `search` and `eval` (phase A had only `--no-place-filter`, with the
  filter on).
- **Landmark radius 0.5 km** (phase B; was 1.0 km), `stages.places` "2".
- **Fallback order:** the place is dropped before the date. With the place dropped, a search behaves exactly as
  in P1.7.
- **Three tables, not one.** The acceptance list names `photo_places`. `places` (id, name) and `place_names`
  (lookup keys) sit beside it, so search resolves names from the DB alone.
- **`countryInfo.txt` is downloaded too** (8 KB), for the country's plain name ("India", not the dump's
  "Republic of India").
- **City vs. district/state.** The city is the nearest town of ≥ 1,000 people. District and state come from the
  nearest populated place of any size, so border photos (Noida) get the right state.
- **The text side of the filter skips `place` rows.** A Noida photo's place text contains "New Delhi", which
  must not match "Delhi". GPS places are matched by id.
- **Smaller changes:**
  - The bot's `search_dates` is gone; captions use `Result.date`.
  - `query_words` moved to `search/words.py` (import cycle `search.text` ↔ `store.places`).
  - The eval's "no captions" retriever now includes `place` rows.
  - `imgsearch run filename` and `run places` no longer need the pen drive (both read only the DB).
  - `rewrite` prints `ParsedQuery` without `place_filter` (search sets it, not the rewrite).
- **T5:** `local_files_only=True` instead of setting `HF_HUB_OFFLINE=1`. It covers only SigLIP and doesn't
  change the process environment. The captioner (`mlx_vlm.load`) is unchanged.

## Flags

- **City names are often urban villages or suburbs.** Examples: Saidabad and Saiyad-ul-ajaib for Delhi photos;
  Lohogaon, Khadki and Vagholi for Pune; Dabolim for Goa; Amber Fort → "Ākera".
  - Search isn't affected: district and state carry "Delhi", "Pune", "Goa".
  - But labels read like "Saidabad, South East, Delhi".
  - A second, larger "city" level (e.g. the nearest place of ≥ 100,000 people) would read better. It needs a
    migration and a re-run; not done.
- **GeoNames admin errors:** the 22 photos near Pahalgam (Kashmir, 20 July 2024) get state "Ladakh" from the
  nearest village's admin code.
- **"Jaipur" doesn't resolve.** The 2023 "Jaipur trip with my coworkers" GPS shows Bhilwara, Chittorgarh and
  Jaisalmer. Either the trip didn't reach Jaipur, or those photos have no GPS.
- **"Pune Division"** is GeoNames' admin2 name for Pune; "Pune" resolves through the city and the division's
  alternate name.
- **Short alternate names** of 3+ letters (airport codes such as JAI, DEL, BLR) are lookup keys. Not seen in the
  evals.
- **A hard place filter drops photos without GPS** (534 of 1,442) unless their text names the place, and its text
  side matches any OCR mention (a flight booking to Goa). That is why it is off.
- **Bot:** the running bot (started 20:44, main at `9c0fdfe`) still has the pre-P1.8 code. Captions with places
  and the place-fallback note need a restart. Migration 005 is already applied, so a restart needs nothing else.
