# P1.8 report: places from GPS (offline reverse geocoding) and place-aware search

Phase A (code and tests): 2026-10-21, branch `p1.8` in `.worktrees/p1.8`, rebased on `main`
at `9c0fdfe` (P3-T merged and reviewed). Phase B (real run, evals, merge) waits for the
user's go.

## Summary

- **`imgsearch geo download`** fetches the GeoNames files once into git-ignored `data/geo/`:
  `IN.zip`, `admin1CodesASCII.txt`, `admin2Codes.txt` and `countryInfo.txt`. A file already
  there is skipped; `--force` downloads it again. `MANIFEST.tsv` records each file's size,
  SHA-256, URL and download time. The zip is read in place, never extracted.
- **`places` stage** (no model, no pen drive, `requires: ["ingest"]`):
  - For each photo with GPS it records the nearest city, its district, state and country,
    and the nearest landmark within 1 km, with distances.
  - Uses numpy haversine over a bounding box. No new dependencies.
  - Migration 005: `photo_places`, `places`, `place_names`.
  - The names also go into `text_fts` as kind `place`.
  - Runs in `imgsearch run places` and in `update` after `filename`. `status` shows GPS
    coverage and places resolved.
- **Place-aware search.** The rewriter's `place` is used only if it resolves, through
  `place_names` (GeoNames names and alternate names, in any script), to a place some photo
  was taken at.
  - Then every retriever keeps only photos from there (at any level: a state matches its
    cities) or whose OCR, caption or file-name text contains the name.
  - It combines with the P1.7 date filter. If nothing survives, the place is dropped first,
    then the date.
  - `SearchResponse.place_filter` / `place_fallback`; `--no-place-filter` on `search` and
    `eval`.
- **Results show date and place** (`Result.date`, `Result.place`), in the CLI and in the
  bot's captions ("3 · 2023-12-30 · Amber Fort, Amer, Jaipur, Rajasthan · …"). The bot
  explains a place fallback in a text message.
- **Search needs no GeoNames files and no network**: it reads only the DB.
- **Tests:** 540 pass (P3-T's merged main had 486), ruff clean. 54 new in
  `tests/test_places.py` (synthetic GeoNames files in `tmp_path`, an `httpx.MockTransport`
  for the download) and 1 in `tests/test_chat_bot.py`.

## Changes from the plan

All recorded in the plan (new D22; P1.8 entries in "Changes during build"):

- **Interface changes:**
  - `ParsedQuery.place_filter` (new `PlaceFilter` type), set by `Searcher`. Every
    `Retriever` must honour it, as with `date_range`.
  - `Result.date` and `Result.place`.
  - `SearchResponse.place_filter` / `place_fallback`; `Searcher.search(place_filter=)`.
- **Fallback order:** the place is dropped before the date. With the place dropped, a
  search behaves exactly as in P1.7.
- **Three tables, not one.** The acceptance list names `photo_places`. `places` (id, name)
  and `place_names` (lookup keys) sit beside it, so search resolves names from the DB
  alone.
- **`countryInfo.txt` is downloaded too** (8 KB), for the country's plain name ("India",
  not the dump's "Republic of India").
- **City vs. district/state.** The city is the nearest town of ≥ 1,000 people. District
  and state come from the nearest populated place of any size, so border photos (Noida)
  get the right state.
- **The text side of the filter skips `place` rows.** A Noida photo's place text contains
  "New Delhi", which must not match "Delhi". GPS places are matched by id.
- **The bot's `search_dates` is gone:** captions use `Result.date`.
- **`query_words` moved to `search/words.py`** (import cycle `search.text` ↔
  `store.places`).
- **The eval's "no captions" retriever** now includes `place` rows.
- `imgsearch run filename` and `run places` no longer need the pen drive (both read only
  the DB).
- `rewrite` prints `ParsedQuery` without `place_filter` (search sets it, not the rewrite).

## Flags

### For phase B

- **Small towns win over the city next to them.** Amber Fort → "Ākera", Cyber Hub →
  "Rijokri". District, state and landmark are right, so "Jaipur" and "Gurgaon" still find
  them. Check the real top-15 table. If it reads badly, raise `city_min_population` or
  prefer larger places within a few km.
- **"Pune Division"** is GeoNames' admin2 name for Pune. "Pune" still resolves through the
  city.
- **Short alternate names** of 3+ letters (airport codes such as JAI, DEL, BLR) are lookup
  keys. A rewriter `place` of "DEL" would resolve to Delhi. Not seen in practice; noted.
- **bm25 shift:** 908 short `place` rows join `text_fts`, as the `filename` rows did in
  P1.7. Hybrid scores move a little; the before/after eval shows how much.
- **The place filter's text side is broad by design.** A screenshot whose OCR says "Goa"
  (a flight booking) passes the "Goa" filter.

### For later tasks

- **P2 (Takeout):** photos that gain GPS from Takeout JSON were already marked done by
  `places`. Clear their `places` rows in `stage_status`, or bump `stages.places`, after
  adding GPS.
- **P2:** if the library has photos abroad, add those countries to `places.countries` and
  run `geo download`. `status` shows how many GPS photos got no place.
- **Restaurants and shops** (user question, 2026-10-21: "inside a restaurant with name
  barbecue nation?"): GeoNames has 17 restaurants for all of India and no Barbeque Nation.
  Such a photo gets its area, not its name. Naming businesses from GPS would need an
  OpenStreetMap extract (much larger, needs its own task). Until then those photos are found
  by OCR/caption text and dates.
