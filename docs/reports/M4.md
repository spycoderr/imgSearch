# M4 report: caption stage

2026-10-20

## Summary

The `caption` stage captions each derivative with `mlx-community/Qwen3-VL-4B-Instruct-4bit`
through mlx-vlm 0.7.9 (`MlxCaptioner`), and stores the text through `store.text.save_caption`
in `captions` and `text_fts` (kind `caption`). All 130 photos are captioned: 130 done, 0 failed.
A second run processes 0. The run took 755.5 s, about 5.8 s per image. MLX peaked at 3.96 GB,
and the process's peak memory footprint was 5.84 GB. `unload()` brings MLX memory back to 0.00 GB.
`imgsearch run caption` is the entry point (`"caption"` was added to `STAGES` in `cli.py`).
`uv run pytest` (134 tests, 18 of them M4's), `ruff check` and `ruff format --check` pass.

Supervisor decisions applied: Q3, the ~1 MP area cap, is recorded in the plan. Q4: `max_tokens`
was lowered from 200 to 100, a prompt variant was tried on 10 varied images before the full
run, no filler is stripped in code, and the filler rate is reported below. Q5: the README
section is kept. The test-injection convention is the one recorded in the plan as S4
("M3 – test injection for stages").

### Prompt trial (Q4), 10 images, before the full run

The images were 2 food, 1 people, 1 mountains, 1 temple, 2 signs, 2 dense documents and
1 street. They were chosen with `search-vec` and the OCR text lengths.

| Prompt | "No … text" filler | Verbatim text |
| --- | --- | --- |
| A (phase A prompt, kept): "…in one or two short English sentences. If the photo contains readable text, add it after the description, copied exactly. Do not mention text if there is none." | 4 of 10 | Signs and lists copied line by line (Dubai Bazaar store list, IIT Delhi sign, candy list, school header) |
| B: "…If any words are written in the photo, copy them exactly after the description." | 3 of 10 | Mostly paraphrased ("The text includes the school name…"); the Dubai Bazaar and IIT Delhi sign text was dropped |

Prompt A was kept because verbatim text is what full-text search can match. B removes one filler
sentence but replaces copied text with prose about "the text".

## Benchmark

Full details are in `docs/benchmarks.md` ("M4: caption"). Measured on the Mac mini M4 with no
other model running.

| Measure | Value |
| --- | --- |
| Total wall time, 130 images (incl. startup and load) | 755.5 s |
| Import mlx-vlm / model load | ~3 s / 2.2–2.5 s |
| Seconds per image, mean / median / min / max | 5.8 / 6 / 3 / 7 (1 s resolution, from `stage_status.updated_at` gaps) |
| MLX memory: loaded / peak / after `unload()` | 3.10 / 3.96 / 0.00 GB |
| Max RSS / peak memory footprint | 3.88 GB / 5.84 GB |
| Projected for 40k photos | ~64 h (~2.7 days) |

For comparison, embedding takes 0.06 s per image (~40 min for 40k) and OCR 0.24 s (~2.7 h for 40k).

### Recommendation (acceptance item 11)

**Caption everything, but last and in the background (D17), and confirm with the M7 eval before
the bulk run.** These are the reasons, from the numbers:

- **Cost:** ~64 h of unattended compute for 40k photos. That is affordable for a one-off
  backfill on a Mac that is otherwise idle. Memory is ~4 GB of MLX, 5.8 GB footprint at peak,
  which fits in 16 GB next to a desktop as long as no other model is loaded.
- **"Caption only text-bearing images" saves little and keeps the wrong part.** OCR already
  stores the text, and Vision found text in 69 of 130 photos. A caption's added value is the
  scene description ("beach", "dog", "candy list"), which OCR can't give. The photos without
  text (61 of 130 here) are where captions add the most.
- **Skip captions** if M7 shows hybrid recall@5 doesn't improve with captions over
  vector + OCR. That would save the 64 h. The decision belongs to the M7 eval, not to this
  benchmark.
- If time matters, `max_tokens` can be lowered further, since descriptions rarely need
  100 tokens. Copied text on dense pages would be cut shorter, but OCR holds the full text.
  This wasn't measured.

## Changes from the plan

Recorded under "Changes during build" in the plan doc:

- **M4 – caption images are capped by pixel area, not long edge** (`max_pixels` = 1024×1024).
  The panorama goes to 3581×292 instead of 1024×83. Q3.
- **M4 – caption settings in `models.captioner`** (`prompt`, `max_tokens: 100`, `max_pixels`),
  greedy decoding with an explicit `temperature=0.0`, and cleaning limited to chat-template tokens
  and a leading "Caption:". Q4.
- **M4 – `CaptionStage(config, load_captioner=...)`**, following the S4 convention, with a lazy
  mlx-vlm import.

The plan's M4 text says "extend `TextRetriever` to search captions as well". M3's
`TextRetriever` already searches all of `text_fts`, so no retrieval code changed (wave rules).

## Flags

- **Filler is 35% (45 of 130).** "No readable text is present." matches FTS queries containing
  `readable` (44 captions), `text` (66 captions, including real "The text reads…" phrases) or
  `visible` (38). M3's stopword list doesn't drop these words. Accepted for the MVP under Q4.
- **Greedy decoding loops on 2 of 130 photos** ("54 / 54 / …", "CUBIC BAND …"), until
  `max_tokens` stops them. This is harmless for search, apart from repeated tokens. A
  `repetition_penalty` (an mlx-vlm `generate` option) would be the fix, if wanted later.
- **Copied text isn't always exact.** "Rit Kat" for Kit Kat and "Deebe Mint" in the candy list,
  and "GOME, and AOTHER" on a restaurant sign. OCR remains the main text signal.
- **Correction to my phase A hand-back.** It said the set has no text-heavy photos. It has many
  photographed documents (school assignments, textbook pages), with up to 2,127 OCR characters.
  There are still no screenshots or PNGs. Text capture was checked on these in the 10-image trial.
- **The prompt has 1–2 sentences, but 37 descriptions have 3.**

### For M5 and M7

- Every image now has a caption in `captions.text`, so `Result.caption` can be filled from
  that table.
- Captions about people often contain "people", "man", "woman", "boy", "photo shows". Those
  generic words will match many captions in FTS; M7's ablations should show whether the text
  retriever needs a larger stopword list.
- Caption runs need ~4–6 GB. Don't run them while the embedder and the rewriter are loaded for
  search.
