# M3 report: OCR stage and text retriever

2026-10-20

## Summary

M3 adds Apple Vision OCR (`AppleVisionOCR`, through `ocrmac`), the `ocr` stage, the
`TextRetriever` over all of `text_fts`, and two commands: `imgsearch search-text` and the
generic `imgsearch run <stage>`. Phase A was built in `.worktrees/m3`. Phase B addressed
supervisor item S3 (stopwords) and S4 (the test-injection convention in the plan), rebased on
`main` and merged fast-forward. On the 130 real photos: 130 done, 0 failed, and a second run
processed 0. 69 images have non-empty OCR text and 61 have `""`. `uv run pytest` (100 tests),
`ruff check` and `ruff format --check` pass.

## Changes from the plan

Recorded under "Changes during build" in the plan doc:

- **Test injection for stages (S4).** Stages take an optional constructor argument that
  supplies the model; `load` builds the real one when it is omitted. `OcrStage(config,
  engine=None)`. Recorded once for M2 and M4 to reference.
- **`imgsearch run <stage>`** with a `STAGES` dict in `cli.py`. Only `ocr` is listed;
  ingest keeps its own command.
- **`models.ocr`** config section (`recognition_level: accurate`, `languages: ["en-US"]`), and
  the ocrmac known gap (Q1).
- **One FTS query for `english` and `original`.** The words of both fields go into one
  `OR` query, deduplicated per image at the best bm25 row, instead of two queries merged
  afterwards. `Candidate.score` is `-bm25` (higher is better).
- **Stopwords (S3).** A fixed list of English stopwords plus `photo(s)`, `picture(s)`,
  `image(s)`, `pic(s)` is dropped from queries, case-insensitively. A query of only such
  words returns `[]`. Note `and`/`or` are in the list, so a typed `AND` is dropped too.

## Flags

- **Known gap: Vision failures are stored as no text (Q1, accepted).** ocrmac returns `[]`
  without raising when the Vision request fails, so such an image is `""` and `done`.
  Baseline: 61 of 130 images have empty text. A noticeable rise in that share on new data
  would point to this.
- **Three tests call real Apple Vision (Q2, accepted):** two-line reading order, blank image,
  and `run ocr` end to end. Under 1 s together.
- **No stemming.** `pizza` does not match `pizzas`; `skittle` would not match `Skittles`.
- **`bm25()` can't be used under `GROUP BY`** in SQLite, so the one-row-per-image dedupe is
  done in Python over rows ordered by bm25.
- **Handwriting OCR is poor.** Many of the 69 text images are handwritten notes; their text is
  mostly garbled and rarely useful for search. Printed signs, screens and sheets read well.
- **Duplicates crowd the top 3.** Queries for the IIT sign or the shop list fill the top 3
  with near-duplicate photos of the same thing (P6 near-dup grouping addresses this).
- **README Status paragraph** still says "M1 done ... not yet searched". I only changed the
  M3 row of the status table, since that paragraph is shared text.

### For M4 and M5

- `TextRetriever` already searches caption rows (`kind = 'caption'`); M4 only writes through
  `save_caption`. Stopwords keep caption filler like "This photo shows" from matching
  everything, but content words in filler (e.g. "text", "visible", "readable") are not
  stopwords and will still match (see Q4).
- `search-text` and M2's `search-vec` each look up `orig_relpath` for printing (S5); M5 replaces
  both with one result printer.
- M2 and M4 add their stage to `STAGES` in `cli.py` when they rebase.
