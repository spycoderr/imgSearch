# M1.1 report: ingest follow-up fixes

2026-10-20

## Summary

All six open items from `docs/reviews/M1.md` (R1–R6) are fixed in
`imgsearch/stages/ingest.py`, each with tests. `stages.ingest` is now `"2"`. All 130 real
photos were re-ingested: 130 done at version 2, 0 failed. A second run reports 0 new and
0 processed. The originals are byte-identical, with the same mtimes. `uv run pytest`
(59 tests), `ruff check` and `ruff format --check` pass. The "Deferred" items (D-a, D-b, D-c)
were not touched.

| # | Fix |
| --- | --- |
| R1 | Images with alpha (`RGBA`, `LA`, `PA`, or any mode with `transparency` info, e.g. `P`) are composited onto white before conversion to RGB |
| R2 | The source ICC profile is kept only when the source mode is `RGB`; otherwise the derivative and thumbnail have no profile |
| R3 | Malformed GPS (non-tuple, wrong length, non-numeric parts, a ref that isn't N/S or E/W, NaN) gives (None, None). Exactly (0, 0) gives (None, None), as does \|lat\| > 90 or \|lon\| > 180. No exception reaches the runner |
| R4 | `taken_at` is always naive local time `YYYY-MM-DDTHH:MM:SS`; `OffsetTimeOriginal` is ignored |
| R5 | Derivatives are downscaled only above 2048×1536 = 3,145,728 pixels, keeping the aspect ratio (dimensions floored), and never upscaled |
| R6 | Derivative JPEG quality is 85 (was 90) |

## Changes from the plan

Recorded under "Changes during build" in the plan doc:

- **M1.1: derivatives are capped by pixel area, not long edge (changes D8).** The D8 row in
  the decision log still says "2048px long edge"; the new entry records the change. Quality
  is 85, and D8's 10–15 GB estimate becomes about 21 GB for 40k photos.
- **M1.1: `taken_at` is always naive local time.** This replaces the M1 entry's "includes
  the UTC offset". That M1 entry was left as written.

Other notes:

- **R2 is strict.** Only `RGB` sources keep their profile, as the review says. An `RGBA` PNG
  with an embedded RGB profile loses it. No such file is in the test data.
- **Edits outside ingest.** The `derivatives_root` comment in `config.yaml` and in the README
  no longer says "2048px". In `docs/benchmarks.md`, the M1 section's 40k projection is
  corrected from ~24 GB to ~23 GB (0.58 MB × 40k).

## Flags

- **The task's R5 test asked for a 6656×544 image to keep its size; it doesn't.**
  6656×544 = 3,620,864 pixels, which is above the review's 3,145,728 cap. So the panorama is
  downscaled to 6203×507, as the review's rule requires, and the test asserts 6203×507. The
  4000×3000 → 2048×1536 and 1080×2400 → unchanged cases match the task exactly. If the
  panorama must stay full size, the cap has to rise to at least 3.62 MP.
- **The size saving is small.** R6 brought the average from 0.58 to 0.53 MB, not more,
  because R5 makes 16:9 photos 2364×1330 (3.1 MP) instead of 2048×1152 (2.4 MP).
- **Panorama thumbnails are thin.** The thumbnail keeps a 256 px long edge, so the panorama's
  thumbnail is 256×21. The review didn't cover thumbnails.

### For M2–M4

- Derivatives are no longer at most 2048 px on the long edge. The panorama is 6203 px wide,
  and a 1080×2900 screenshot (3.1 MP) would stay at full size. Models with a fixed input size
  (SigLIP at 384 px) will squash extreme aspect ratios. OCR (M3) gets the full-resolution text.
- `taken_at` has no timezone; treat it as local time.
- Derivatives are always RGB JPEGs, with no alpha and no CMYK profiles.
