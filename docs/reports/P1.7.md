# P1.7 report: file names, dates and weighted merging

## Summary

- **File names and phone folders are search text.** A new `filename` stage (no model) writes one `text_fts` row
  of kind `filename` per photo, from its inbox path (e.g. `Screenshots/Screenshot_…_Gmail.png` →
  `screenshots screenshot gmail`). It runs in `imgsearch run filename` and in `update` after ocr.
- **Migration 004** adds `images.source_relpath` (path inside the inbox) and `images.file_mtime`. `import`
  records both; `imgsearch backfill mtime` and `backfill folders` (Syncthing, read-only) filled them for the
  older photos.
- **Dates.** A photo's search date is `taken_at`, else `file_mtime`. The rewriter's date guard accepts month,
  weekday and relative words in English, Hinglish and Hindi (config word lists). When a query has a date, every
  retriever keeps only photos from those days; if none match, search shows all dates and says so.
  `--no-date-filter` on `search` and `eval`.
- **Weekdays are worked out in code.** In the first after-eval, qwen2.5:7b turned "on saturday" into today's
  date (a Wednesday). Listing the past week in the prompt fixed "kal", "aaj", "pichle hafte" and "pichle
  mahine" but not weekdays, so a weekday in the query now sets the range in code (`rewriter.weekdays`).
- **Weighted RRF.** `search.signal_weights` (default 1.0 each); score = Σ weight / (rrf_k + rank).
- **Default unchanged by the item-15 rule: vector + rewrite, date filter on.** vector+rw recall@5 went from
  0.75 to 0.79 overall: 0.87 → 0.88 on the old 41 and 0.33 → 0.46 on the new 12.
- 380 tests pass, ruff is clean, no new dependencies. Phase A (code and tests) was done in a worktree while P1.6
  ran; phase B (rebase, evals, backfills) on main.

## Flags

- **MVP photos have a copy-date `file_mtime`.** 121 of the 130 MVP originals carry 2026-10-20 as their file
  date (the day they were copied), not the photo's date; the other 9 are evicted and have none. Only one of them has no EXIF date, `IMG_20171115_132546.jpg`,
  so its search date is wrong (2026-10-20). It now appears in "kal" / "yesterday" searches.
- **Date filter on a library-wide single day can surface unrelated photos.** "kal wali shaadi ki photos" now
  shows yesterday's 4 photos (screenshots), as the query literally asks. The eval's `hi-kal-shaadi` expects
  2018 wedding photos and scored 0 before and after.
- **Rewrite noise from the prompt change:**
  - "sortly" → "shortly" helped `u2-sortly-offer`.
  - "Jayapur" → "Jaypur" helped `dv-jaipur-fort` (0.20 → 0.80).
  - "birthday" was dropped from "images from 15-16 sept". The filter still found them.
  - These came from the prompt rewording, not from new matching ability.
- **bm25 shift:** adding 1,442 short `filename` rows changed bm25's corpus statistics. Two hybrid queries lost
  a hit (`u2-networking-notes`, `hi-iit-boy`); keying FTS rows per kind or a separate FTS table would avoid
  this, if it matters at P2 scale.
- **The S3 DB copy predates P1.7's backfills.** The next `imgsearch update` or `upload` refreshes it.
- **For P2 (bulk import):** use Takeout JSON dates where there's no EXIF. The copy should keep the file mtime
  (import already does). Check what mtime WhatsApp images carry (likely the receive date, not the photo date).
- **For P2:** re-measure the weights and the "no captions" hybrid on the full library, where captions will be
  rare. `per_retriever_k` was also only measured at this size.
- **For P3-T (bot):** `SearchResponse` has `date_filter` and `date_fallback`. The bot should say "no photos
  from … ; showing all dates" like the CLI does (`search/show.py`).
- **Still at 0 in every setting:** `u2-profile-photo`, `u2-jaipur-coworkers` and `u2-hsr-su`. They need
  captions, faces/people or GPS (later phases). "HSR" is an abbreviation that no file name or OCR text uses.
