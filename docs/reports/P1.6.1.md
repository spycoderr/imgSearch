# P1.6.1 report: follow-up fixes to P1.6 (review R1–R8)

2026-10-21

## Summary

R1–R8 from the P1.6 review are fixed, each with a test (13 new tests; 305 pass, ruff clean):
- An upload error never stops `update`'s indexing (R1).
- Duplicates of evicted photos import as duplicates (R2).
- Re-ingest restores evicted originals through `fetch` (R3).
- `evict`, `fetch` and `restore-check` stop cleanly when S3 is unreachable (R4).
- Only S3 commands need the bucket and profile (R5).
- `restore-check` reports a bad DB copy as a failure (R6).
- `update` uploads the DB copy last (R7).
- `restore-check` counts what it sampled (R8).

Real checks:
- `status` and `verify` work with the bucket unset; `verify` reports 1,441 of 1,441.
- `restore-check --sample 3`: 3 of 3 plus the DB copy.
- `update` imported a new screenshot and uploaded a DB copy that contains that run's index.
- A second `update` with no new photos ends with `db copy: unchanged since the last copy`.

## Flags

- **For P2 (R3 at scale):** an ingest version bump re-fetches every evicted original onto the pen drive before the next `evict`. At 40k photos (~100 GB) with most evicted, that doesn't fit on the 64 GB drive. Before such a bump, run `evict` during the re-ingest (for example in batches), or re-ingest from the derivatives where the change allows it.
- **For the supervisor:** the real `update` check waited for the caption run (user's choice), because a new phone screenshot had synced into the inbox; running `update` then would have loaded the embedder alongside the caption model.
- **For P1.7:** `update()` gained an `upload_db` argument and `imgsearch/stages/ingest.py` imports `imgsearch.store.cache`; expect small conflicts there and in `importer.py`'s docstring.
- R9 (status stats every original) and R10 (fetch rename) were not in scope, as decided in the review.
