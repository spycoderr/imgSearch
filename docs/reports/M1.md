## Changes from the plan

All of these are recorded in the plan doc under "Changes during build".

- **Ingest is two steps.** `register_new` hashes each file and adds an `images` row for each
  new hash. `IngestStage` is then a normal stage run by `run_stage` and fills in the other
  columns. The runner only works on rows that already exist, so registering can't itself be
  a stage. `imgsearch ingest` runs both steps.
- **Derivative paths are relative to `derivatives_root`:**
  `derivatives/<id[:2]>/<id>.jpg` and `thumbs/<id[:2]>/<id>.jpg`. This keeps absolute paths
  out of the DB.
- **`width` and `height`** are the original's size after EXIF orientation is applied.
- **`taken_at`** falls back to EXIF `DateTime` when `DateTimeOriginal` is missing. It keeps
  the UTC offset when the photo records one.
- **Every run re-hashes every original.** That's fine at MVP size. In P2, files whose path,
  size and mtime are unchanged should be skipped, especially once the originals are on the HDD.

## Flags

- **The 2 "rotated" photos aren't rotated.** `IMG_20170101_000525.JPG` and
  `IMG_20170730_095849.JPG` have EXIF orientation 0, an invalid value meaning "unknown", not
  a real rotation. Ingest leaves them as they are, and both derivatives were checked by eye
  and are upright. Rotation is only exercised by a test with a synthetic rotated image, not
  by the real data.
- **Derivatives are bigger than planned.** At about 0.58 MB each, 40k photos need about 24 GB,
  against the plan's 10–15 GB (D8). Lowering the JPEG quality from 90 would shrink this before
  the bulk run.
- **Exit code.** `imgsearch ingest` exits with status 1 if any file is unreadable or fails to
  process, and lists each one with its error. Failed images are retried on the next run.
