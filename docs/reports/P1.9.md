## Summary

- **Search loads only SigLIP's text tower, on the CPU in float32** (`SiglipTextEmbedder`, SentencePiece
  tokenizer). Search process peak footprint 2.24 → 0.48 GB; total while searching (with `qwen2.5:7b`) 6.89 →
  **5.13 GB**. Query vectors equal the full model's (lowest cosine 0.9999998, 98 texts), so recall is unchanged
  (vector+rw recall@5 0.80 → 0.80 on the same 1,445-photo copy). Warm search 1.72 → 1.55 s. Committed default.
- **Rewriter `gemma3:4b` instead of `qwen2.5:7b`: a decision for the user, not applied.** Total while searching
  5.13 → **2.73 GB** (Ollama 4.65 → 2.25 GB). On the current library (14,871 photos) vector+rw recall@5: overall
  0.681 → 0.683, English 0.664 → 0.653, Hinglish 0.650 → 0.729, **Hindi 0.808 → 0.733** (−0.075: one of 8
  queries; rule 6 allows −0.02). Warm search 1.55 → 2.08 s; cold first search 10.1 → 6.9 s. On the 1,445-photo
  copy in October it passed rule 6 (0.80 → 0.82; Hindi 0.86 → 0.86).
- **Rejected:** float16 or mps for the text tower (same vectors, more memory); `qwen2.5:3b` (Hindi −0.33); num_ctx
  1536 (−0.09 GB on `qwen2.5:7b`, nothing on `gemma3:4b`; kept at 4096).
- **New settings** (`config.yaml`): `models.embedder.query_device: cpu`, `query_dtype: float32`,
  `models.rewriter.num_ctx: 4096`, `eval.memory_queries`. **New commands:** `imgsearch bench-memory`
  (criterion 1) and `imgsearch check-query-vectors`.
- **Interface change:** `TextEmbedder` protocol (`embed_text`); `Embedder` extends it; `VectorRetriever` takes a
  `TextEmbedder`. Recorded in the plan.
- **Tests:** 660 pass (649 on main + 11 P1.9), ruff clean.

- On CPU in float32 the weights stay memory-mapped (clean file pages, not footprint). Casting to fp16 copies them, so
  fp16 raises the footprint everywhere. On mps, ~1 GB of IOAccelerator memory stays after `empty_cache`.

  0.9999981; bf16 0.9999048.
- SentencePiece `token_ids` vs the HF tokenizer: 110 texts (eval queries, baseline English rewrites, rewrite examples,
  edge cases), 1 differs: a literal "<pad> <eos>" typed as text.
- Torch + transformers imports alone: ~0.28 GB footprint that stays after an unload (the leak criterion's +50 MB
  can't hold in-process).

## Flags

- **Rule 6 is decided by single queries for Hindi.** Hindi has 8 queries, so one query moves Hindi recall@5 by
  ~0.1; the 0.02 limit can't separate noise from a real change. `gemma3:4b` is +0.08 on Hinglish (14) and −0.075 on
  Hindi (8) on the current library, and +0.02 on the two together. More labelled Hindi queries would make the
  rule meaningful.
- **`gemma3:4b` often leaves an English query unchanged** (e.g. "give me some images of …"), where `qwen2.5:7b`
  strips the request words. That helped one query and hurt two. The prompt could ask for the request words to be
  removed; not tried (outside this task's scope without a decision on the model).
- **Criterion 5 (Should) is not met as written:** after the unload the process keeps ~0.37 GB more than before
  loading (torch and transformers imports, ~0.28 GB, plus Python/SQLite). It does not grow with the number of
  searches (+303 MB after 10 and after 50 on the 1,445 copy). Only a searcher in a subprocess would return within
  50 MB; not built (no measured need: the idle bot then holds ~0.45 GB).
- **The leftover ~1 GB of Metal memory on mps** after `torch.mps.empty_cache()` is avoided by running the text
  tower on the CPU. Image embedding (`embed` stage, mps) still has it, but that runs in a short-lived process.
- **Literal `<pad>` / `<eos>` typed in a query** are plain text for the SentencePiece tokenizer and special tokens
  for the HF tokenizer (1 of 110 test texts differs). Nobody types these.
- **Variant measurements in October were on 1,445 photos**; the confirmation covers only the two rewriter
  options on 14,871 photos. The embedder variants (mps, fp16) are memory-only and don't depend on library size.

### For the user (decision)

- Switch the rewriter to `gemma3:4b`? Saves 2.4 GB while searching (5.13 → 2.73 GB); overall recall@5 the same
  (0.681 → 0.683), Hinglish better (0.650 → 0.729), Hindi worse by one query (0.808 → 0.733), English −0.011;
  warm search +0.5 s (1.55 → 2.08 s), cold first search −3.2 s. The model is already pulled. To apply, in
  `config.yaml`:

  ```yaml
  models:
    rewriter:
      name: "gemma3:4b"
      num_ctx: 4096
  ```

  then `launchctl kickstart -k gui/$UID/com.imgsearch.bot`. The README's model table and `ollama pull` line and
  plan D5 change with it (`docs/RESTART.md` is local and names no rewriter model).
