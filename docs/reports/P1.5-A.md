# P1.5-A report: import from the inbox, storage on the pen drive

2026-10-20 to 2026-10-21

## Summary

- **Storage layout (D18).** Originals and derivatives are on the pen drive under
  `${IMGSEARCH_STORAGE_ROOT}` (set in the git-ignored `.env`; `.env.example` committed). The DB,
  the thumbnails (`thumbs_root: data/thumbs`) and the inboxes (`data/inbox/phone`,
  `data/inbox/camera`) are on the Mac. A `db_path` under `/Volumes/` is rejected.
- **Migration 002** made `thumb_path` relative to `thumbs_root` and `derivative_path` relative
  to `derivatives_root` (both `<id[:2]>/<id>.jpg`).
- **Pen-drive check.** `import`, `update`, `ingest`, `verify` and `run <stage>` stop with
  "pen drive not mounted: …" before doing anything. `search` and `status` work without the
  drive; `search` says full-size images are unavailable.
- **New commands:**
  - `imgsearch import`: inbox → `originals_root/YYYY/MM/<name>`, with a verified copy, then the
    `images` row, then the inbox file is deleted.
  - `imgsearch update`: import, then ingest, embed and ocr. No captions.
  - `imgsearch verify`: originals by SHA-256; derivatives and thumbnails must exist and decode.
- **Hook.** The originals-protection hook expands `${IMGSEARCH_STORAGE_ROOT}` from the
  environment or `.env`. If it can't, it protects the unexpanded path and `data/originals`
  and says why.
- **Real run.** The 130 existing photos were moved; the user ran the one originals copy
  command. Then 1,311 phone photos were imported from the two Syncthing folders, and all
  1,441 images are done for ingest, embed and ocr, with 0 failed. `verify` passes for
  1,441 of 1,441. A second `update` does nothing. Syncthing doesn't re-download the deleted
  inbox files.
- **Checks.** `uv run pytest` passes (263 tests; 41 new), and so does ruff. The tests also
  pass with `.env` removed. No dependency beyond `python-dotenv`, which the user asked for.
- **Commits.** The code is on `main` in `30cb731`, not pushed. It replaces an earlier,
  unpushed commit (`d10fb5a`) that had the drive path in `config.yaml`. `git grep` for the drive's name
  finds only the two supervisor docs (plan D18 and `docs/acceptance/P1.5-A.md`).

### exFAT overhead (measured; accepted by the user for now)

- The drive's allocation block (cluster) is 128 KiB.
- macOS adds a protected `com.apple.provenance` extended attribute to every file it creates.
  exFAT can't store it, so macOS writes a hidden `._<name>` file (4 KB of data, one cluster)
  for every file and folder. `xattr -d com.apple.provenance` doesn't remove it (tested on a
  scratch file).
- Measured on the final 1,441 photos:

| | Files | `._*` files | Data | On disk (`du`) | Extra |
| --- | --- | --- | --- | --- | --- |
| originals | 1,441 | 1,496 | 3,630 MB | 3,928 MB | +298 MB (+8%) |
| derivatives | 1,441 | 1,697 | 700 MB | 1,050 MB | +350 MB (+50%) |
| total | 2,882 | 3,193 | 4,330 MB | 4,978 MB | +648 MB (+15%), ~0.45 MB per photo |

- Projection for 40k photos: about 18 GB of overhead on a 57 GiB drive.
- The user decided to keep exFAT for now. Reformatting to APFS is a later step for the
  supervisor to plan. The code does nothing about `._*` files; every scanner skips them as
  hidden files.

## Changes from the plan

Recorded under "Changes during build" in the plan doc (P1.5-A entries):

- **`.env` for machine paths** (user decision during the task). `${VAR}` in path fields only;
  the environment wins over `.env`; an unset variable fails naming it.
  `load_config(path, env_file)` takes the `.env` path so tests don't depend on the machine.
- **Both path columns changed,** not only `thumb_path`: `derivative_path` lost its
  `derivatives/` prefix, since derivatives now have their own root. This changes the M1
  layout entry and `Result.thumb_path`'s base.
- **`import` adds two safety rules** to the acceptance list:
  - a duplicate is deleted from the inbox only if its registered original exists; otherwise
    it's a failure and the file stays;
  - a target that already holds the same bytes (left by an interrupted run) is reused.
  - Also, the copy keeps the source mtime.
- **`import` registers rows itself,** so `update` doesn't scan `originals_root` (D-b).
  `imgsearch ingest` still exists for that.
- **`verify` checks derivatives and thumbnails by decoding, not by hash.** The DB stores no
  hash for them. The one-off move of the 130 was checked by hash against the old copies
  (above).
- **The fsync is `os.fsync`.** On macOS that doesn't force the drive's write cache; the README
  says to eject before unplugging.

## Flags

- **The 1,311 imported photos have only one copy on the Mac side, on the pen drive** (the
  phone keeps its own). Until P1.6 (S3), losing or reformatting the drive loses them. Copy
  `$IMGSEARCH_STORAGE_ROOT` off the drive before any reformat.
- **exFAT overhead:** ~0.45 MB per photo, ~18 GB for 40k (above). Accepted for now.
- **Ingest is about twice as slow on the drive:** 0.093 s per image, against 0.044 s from the
  Mac's disk in M1.1.
- **The phone folder holds the phone's whole Pictures tree,** not just the camera:
  screenshots, WhatsApp, Reddit, Twitter, game screenshots. All of it is now indexed. Filed
  by EXIF date, else by the phone's mtime: 196 of the 1,311 have no EXIF date.
- **Hook coverage changed with the config.** It now protects the pen-drive originals.
  `data/originals` is no longer protected while `.env` resolves (it's no longer the
  originals root). It still holds the user's 130 original files until the user deletes it.
- **The hook is still best effort.** A Python script writing a file isn't caught. This
  task's one-off copy script wrote only derivatives and thumbnails.
- **Acceptance item 17 was checked with photos already synced** before the task, not with a
  photo taken during it. The path is the same (Syncthing → inbox → `update` → search).
- `cli.py` is 300 lines (the "Should" is about 200). The new commands only print; the logic
  is in `sources/importer.py`, `stages/update.py` and `store/verify.py`.
- The README's model table said `qwen2.5:3b`; it now says `qwen2.5:7b` (the M6 choice).

### For P1.6 (cloud originals) and P2

- The originals now sit under `YYYY/MM/` (the 130 older ones are at the top level). S3
  objects are to be named by image id, so the layout doesn't matter there.
- `import` is the only code that adds files under `originals_root`. The P1.6 evictor will be
  the only one that removes them.
- 1,311 images have no captions. Run `imgsearch run caption` in the background if wanted
  (~2 h at 5.8 s each).
