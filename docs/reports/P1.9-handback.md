# P1.9 hand-back: less memory while searching

## Phase A (2026-10-24/25)

- Search now loads only the text part of SigLIP, on the CPU. The search process uses 0.4–0.5 GB instead of
  2.2 GB. The query vectors are the same as before, so results don't change.
- New commands: `imgsearch bench-memory` measures memory and speed while searching, and
  `imgsearch check-query-vectors` checks that the vectors still match the full model.
- Tried and dropped: float16 and the GPU for the text model (they use more memory) and `qwen2.5:3b` (much worse on
  Hindi). A smaller Ollama context (`num_ctx`) saves almost nothing, so it stays at 4096.

## Confirmation on the merged code (2026-11-11)

- `main` (dedupe, persons, search by person, P5-live docs) is merged into `p1.9`. 660 tests pass and ruff is
  clean. The measurements ran on a copy of the main DB with 14,871 photos. Nothing on the main DB, originals,
  pen drive or S3 was written. I waited for the P5-live job's lock before I started.
- Memory while searching:
  - before P1.9: 6.89 GB
  - now, with `qwen2.5:7b` (the default): **5.13 GB**. Recall is unchanged (0.68), and a warm search is a little
    faster (1.55 s).
  - with `gemma3:4b`: **2.73 GB**

## Your decision: switch the rewriter to `gemma3:4b`?

- Saves 2.4 GB while searching (5.13 → 2.73 GB).
- Recall@5 on the 57 queries:
  - overall: the same (0.681 → 0.683)
  - Hinglish: better (0.650 → 0.729)
  - English: slightly lower (0.664 → 0.653)
  - Hindi: lower (0.808 → 0.733). That is one query of 8 ("समुद्र किनारे लड़का"), but it's more than the 0.02
    the rule allows. In October, on 1,445 photos, Hindi didn't drop.
- A warm search is ~0.5 s slower (2.1 s). The first search after idle is ~3 s faster.
- I didn't change `config.yaml`. To switch, set `models.rewriter.name: "gemma3:4b"` and restart the bot. The
  model is already pulled.

## Also open
