# P1.6 report: originals encrypted in S3, pen drive as an LRU cache

2026-10-21

## Summary

Every one of the 1,441 originals (3,630 MB) and an encrypted copy of the DB are in S3 Glacier Instant Retrieval (ap-south-1), each encrypted on the Mac with AES-256-GCM and verified against S3's checksum of the exact version written. The upload took 433.5 s (8.4 MB/s) with 0 failures; a second run uploaded 0. A restore check of 10 random originals and the DB copy passed. Eviction removed the 10 least recently used originals with a 3.624 GB cap (dry run first), `fetch` restored one byte-for-byte with its mtime, and `verify` passed (1,441 of 1,441). Estimated storage cost: $0.018/month now, about $0.50/month at 40k photos.

The first upload attempt recorded nothing: the IAM user lacked `s3:GetObjectVersion`, so the verify step got 403. The user added the permission; no code change was needed. `search` was not run, per the supervisor's instructions.

### Cost estimate (item 21)

Prices, ap-south-1 (Mumbai), checked 2026-10-21: Glacier IR storage $0.005 per GB-month (costgoat.com regional table; us-east-1 is $0.004). PUT $0.02 and GET/HEAD $0.01 per 1,000 requests, retrieval $0.03 per GB (published us-east-1 figures; Mumbai's not found, likely similar). Upload traffic into S3 is free. Minimums: 90 days of storage per object version, 128 KB per object.

Real numbers: 1,441 objects, 3.63 GB, 2.52 MB per original on average; 83 objects under 128 KB (adds < 0.01 GB billable). DB copy 10.8 MB per version.

| Item | 1,441 photos (real) | 40,000 photos (scaled at 2.52 MB each = 101 GB) |
| --- | --- | --- |
| Storage | 3.63 GB × $0.005 = **$0.018 / month** | 101 GB × $0.005 = **$0.50 / month** ($6 / year) |
| Upload requests (one-off) | 1,441 PUT ($0.029) + ~2,900 HEAD ($0.029) = **$0.06** | 40k PUT ($0.80) + ~80k HEAD ($0.80) = **$1.60** |
| This run's failed first attempt | 251 extra versions, 0.65 GB × 3 months minimum = $0.01, plus 251 PUTs $0.005 | n/a |
| DB copies | 10.8 MB per changed `upload`; the bucket lifecycle expires old versions after 90 days, so at most ~90 copies ≈ 1 GB = $0.005 / month | ~300 MB per copy (estimate) × up to 90 = 27 GB ≈ $0.14 / month if uploaded daily |
| Fetching one original | $0.00008 retrieval + 1 GET; transfer out is within AWS's 100 GB/month free allowance | same per photo |
| Full restore of every original | 3.63 GB × $0.03 = $0.11 | 101 GB × $0.03 = $3.03 retrieval, plus transfer out above the 100 GB free allowance |

Matches D19's "about $0.40 per 100 GB per month" within the Mumbai price difference (+25%).

## Changes from the plan

Recorded in the plan under "Changes during build" (eight P1.6 entries):

- `cli.py` split into `imgsearch/commands/` (review A5); `cli.py` is 46 lines.
- New `ObjectStore` protocol, `ObjectInfo` and `StoreUnavailable` in `interfaces.py` (a new seam; nothing deletes).
- The plan's `in_s3` flag became the `s3_copies` table, plus `original_cache` (migration 003), with an extra `orig_mtime_ns` column so `fetch` restores the mtime.
- Encryption format, key in the Keychain, S3 settings in `config.yaml`/`.env`, single `PutObject` per object (no multipart).
- DB copy skipped when unchanged; `update` = import → upload → ingest → embed → ocr; evict/fetch/verify/restore-check behaviour.

New dependencies: `boto3` (the S3 client, used only in `imgsearch/store/s3.py`, imported lazily) and `cryptography` (AES-256-GCM; the standard library has no authenticated encryption).

IAM: the IAM user needed `s3:GetObjectVersion` in addition to put/get; the user added it during this task. README now lists the three permissions.

## Flags

- **For the user:** the 1,311 phone photos now have a verified encrypted S3 copy, so review notes A1 (don't wipe the drive before P1.6) and A4 (delete the old `data/originals` and `data/derivatives` copies once P1.6 has a cloud copy) can now be acted on, and P4b (reformat the pen drive to APFS) is unblocked, as far as the S3 side goes. The key is the single point of failure: the Keychain item and the user's saved copy (they match).
- **For the user:** 9 originals stay evicted (`IMG_2016…`–`IMG_2019…`). `imgsearch fetch <path>` brings any back.
- **For the supervisor:** `search` was not run (per instructions), so acceptance item 20's "search still shows it" is shown by DB evidence instead. Run `imgsearch search` or the next `eval` once the caption job ends.
- **For the supervisor:** the IAM user can't list object versions (`s3:ListBucketVersions`), so item 17's "list object versions" was shown indirectly (versioning `Enabled`; a key uploaded twice has a new latest version). Adding that permission is optional; the code doesn't need it.
- **For the supervisor:** about 251 orphan object versions from the failed first attempt (0.65 GB). The lifecycle rule expires them 90 days after they become noncurrent. Cost under $0.01.
- **For P2:** an upload whose verify step fails leaves an unrecorded object version behind (as happened here). Harmless, but a loud error on the first failure of that kind would have saved 250 wasted puts. Consider stopping the run after a few identical failures.
- **For P2:** every `upload`/`update` that follows a DB change uploads a full DB copy (10.8 MB now, maybe ~300 MB at 40k). Fine with the 90-day lifecycle (≈ $0.14/month worst case), but an incremental scheme or a daily limit may be worth it later.
- **For P2:** single `PutObject` (5 GB limit) and whole-file reads in memory are fine for photos (largest 19.3 MB); videos from Takeout may need multipart and streaming.
- **For P2:** S3 rate was 8.4 MB/s, so 100 GB takes about 3.3 hours.
