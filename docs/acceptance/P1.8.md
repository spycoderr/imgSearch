# P1.8 acceptance criteria: places from GPS (offline reverse geocoding) and place-aware queries

Blocking unless marked "Should". Goal: "photos from Goa", "Jaipur ka kila", "India Gate outing", "Rajasthan trip"
find photos by **where they were taken**, entirely offline. Builds on P1.7's date filter pattern.

## Starting facts (2026-10-21)

- 908 of 1,442 photos have GPS (`images.lat/lon`); main clusters: Delhi/Noida, Mussoorie/Dehradun, Pune, Goa.
  The 130 MVP photos and most screenshots have none. P2's Takeout JSON will add GPS for more.
- The rewriter already returns a `place` field, but it also emits non-places ("park", "sofa": M6); MVP search
  ignores it. Captions sometimes name places ("Amber Fort in Jaipur").
- Default search is vector + rewrite with a date filter (P1.7); hybrid is `--signals vector,text`.

## 3. Place-aware search

| # | Criterion | How to verify |
| --- | --- | --- |
| 7 | The rewriter's `place` is used **only if it resolves** to a name present in the library (`photo_places` city/district/state/country/landmark, matched case-insensitively against GeoNames names **and alternate names**, so Bengaluru/Bangalore, Gurugram/Gurgaon and Devanagari names like जयपुर all work). Unresolvable "places" (park, sofa, home) are ignored | Tests incl. those examples |
| 8 | When it resolves, candidates are **filtered** to photos whose GPS place matches at that level (a state query matches all its cities), **or** whose caption/OCR/file-name text contains the place name (covers photos without GPS) | Tests |
| 9 | Combines with the date filter (both must hold). If nothing survives, fall back like dates do and say so (`SearchResponse` flag; CLI and Telegram bot show it) | Tests |
| 10 | `--no-place-filter` for the CLI and the eval | Test |
| 11 | Should: the CLI shows each result's place ("Amer, Jaipur, Rajasthan") next to its date; the Telegram caption line too | Read output |
