# P2 acceptance criteria: bulk import (Google Takeout) at archive scale

Blocking unless marked "Should". P2 folds in P1.5-B (Takeout import) and the deferred scale items from
earlier reviews. The user starts with **one year** of their own Google Photos before the family archive.
Run P2 only after P1.6.1 and P1.7 are merged (it builds on import, upload, evict and the date/file-name signals).

## 1. Takeout import

| # | Criterion | How to verify |
| --- | --- | --- |
| 1 | `imgsearch import-takeout <zip or folder>` processes **one zip at a time**: unpack to a temp folder on the Mac, import through the same verified copy path as `import`, then delete the temp folder. Never writes into the zip's folder | Tests; real run |
| 2 | Reads Google's JSON sidecars (both `<name>.json` and the newer `<name>.supplemental-metadata.json`, plus Google's truncated names and the `(1)` suffix quirk): `photoTakenTime`, `geoData`, `description`. Fills `taken_at` / `lat` / `lon` **only when EXIF has none**; records the source as `takeout` | Tests with real-shaped sidecars |
| 3 | Album folder names (not `Photos from YYYY`) are kept as the source folder, so they feed the P1.7 file-name/folder text | Test |
| 4 | Skips videos, `-edited` copies (the original is kept), and non-image files; counts each | Test |
| 5 | A photo already imported from the phone (same hash) is a duplicate; a different file of the same scene is **not** deduped here (that's P6 near-duplicates). Report how many Takeout photos were already on the phone | Report |
| 6 | Resumable: a stopped run continues from the next unprocessed zip/file; a zip fully done is recorded and skipped | Test |

## 3. Disk budget (must be decided before the full run)

| # | Criterion | How to verify |
| --- | --- | --- |
| 11 | Before importing, a dry run prints the expected space: originals (cached, capped), derivatives (~0.53 MB/photo), exFAT `._` overhead (~0.45 MB/photo) vs free space on the pen drive and the Mac, and **refuses** to start if the projection doesn't fit | Run it |
| 12 | The run follows the order import → upload → evict (cap) per zip, so the pen drive never holds more originals than the cap | Report: drive usage over the run |
| 13 | Should: if the projection doesn't fit, the report recommends one of: P4b APFS reformat first, a bigger drive, or a smaller derivative size; the user decides | Report |
