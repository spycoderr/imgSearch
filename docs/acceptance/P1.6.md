# P1.6 acceptance criteria: originals in S3 (encrypted), pen-drive cache, fetch on demand

Blocking unless marked "Should". Design: plan D18, D19, P1.6; review notes A1–A5 in `docs/reviews/P1.5-A.md`.
The bucket, the restricted IAM user and the `imgsearch` AWS profile already exist and were verified by the
supervisor: the Mac's key can put/get objects but **cannot delete objects or change versioning/lifecycle**.

## Encryption and objects

| # | Criterion | How to verify |
| --- | --- | --- |
| 5 | AES-256-GCM via the `cryptography` package, a fresh random nonce per object, a small versioned header (format version + nonce) so the format can change later | Read code; tests |
| 6 | Object key is `originals/<image_id>` (the content hash): S3 never sees file names or dates | Test; list one object |
| 7 | Uploads send a SHA-256 checksum of the encrypted bytes (S3 rejects a corrupted upload); the encrypted hash and S3 version id are stored | Read code |
| 8 | Decrypting a downloaded object and hashing it gives exactly the image id, or the fetch fails loudly | Test (incl. a tampered blob) |
| 9 | S3 access goes through a small `ObjectStore` protocol (put, get, head) with a boto3 implementation; tests use an in-memory fake. No moto, no monkeypatching | Read tests |

## Tracking, upload, eviction, fetch

| # | Criterion | How to verify |
| --- | --- | --- |
| 10 | A new numbered migration adds one table for S3 copies (image id, object key, version id, encrypted sha256, size, uploaded_at, verified_at) and a last-access time for cached originals | `.schema` |
| 11 | `imgsearch upload` uploads every original without a verified S3 copy; idempotent; one failure doesn't stop the others; offline gives a clear message and changes nothing | Tests; run twice |
| 12 | `imgsearch update` runs import → **upload** → ingest → embed → ocr. If upload fails (offline), the rest still runs and the summary says how many originals are not yet in S3 | Test with a failing fake |
| 13 | `imgsearch evict` removes least-recently-used originals from the pen drive until under the cap, **only** if the photo has a verified S3 copy **and** its ingest is done. It never touches the DB row. `--dry-run` lists what would go | Tests |
| 14 | `imgsearch fetch <image id or relpath>` returns the local original, downloading, decrypting and verifying it back to its original path when evicted; updates last-access | Tests; real run |
| 15 | `imgsearch status` adds: in S3 (verified) / not yet uploaded / evicted / cache size vs cap | Run it |
| 16 | CLAUDE.md "Originals are read-only" exception list adds `imgsearch fetch` (restores exactly the evicted bytes at the same path) | Read |
